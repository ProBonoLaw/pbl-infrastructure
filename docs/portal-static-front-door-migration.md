# Portal static UI and AKS API migration

The `test` and `prod` stacks each stage a Standard Azure Static Web App, an Azure Front Door Standard profile, and a reserved public IP for a second AKS application-routing controller. Test retires its Node Web App after its public hostname moves to Front Door. Production retains the old site until its apex cutover is verified. New resource names use `uniqueString(subscriptionId)` so the separate subscriptions get distinct names. Front Door serves the static UI at `/*` and forwards `/api/*` to AKS, both over HTTPS. API responses are not cached. The existing private AKS controller remains the ingress for AIMIE services.

The Front Door origin response timeout is 240 seconds, its maximum. AIMIE QA requests include generation and Markdown formatting and can exceed Front Door's 30-second default. With that default, the browser receives a 504 even while the API continues processing. Operations that exceed four minutes need an asynchronous job flow.

## Provision in each environment

1. Run `npm run verify`, then preview and apply the matching Pulumi stack. Read `portalStaticSiteHostname`, `portalFrontDoorHostname`, `portalFrontDoorGuid`, `portalApiPublicIp`, `portalApiPublicIpName`, and `portalApiOriginHostname` from its outputs. The Front Door endpoint and public IP are unique to that subscription.
2. Create an explicit public DNS **A** record for `portalApiOriginHostname` pointing to `portalApiPublicIp`. The public zone remains hosted at GoDaddy during staging. Test uses `api-origin-testsuffix001` → `203.0.113.154`; Production uses `api-origin-prodsuffix001` → `203.0.113.155`. Both records already exist. Leave the current production apex A record unchanged.
3. In both environments, the infrastructure deployment workflow installs cert-manager v1.21.2, ensures the API namespace exists, renders the public controller, Let's Encrypt HTTP-01 Issuer, and Certificate from Pulumi outputs, and applies them through AKS Run Command after `pulumi up`. It waits for the Certificate to become Ready and for the trusted `portal-api-tls` secret to exist in `probonolaw-ui`. The API origin A record must resolve before the workflow can complete. Front Door checks the origin certificate name. Production Pulumi grants its deployment identity Azure Kubernetes Service RBAC Cluster Admin on the Production AKS cluster so this cluster-scoped bootstrap can run; the Azure Owner role alone does not grant Kubernetes API permissions.
4. Deploy the API as a Kubernetes `Service` in that namespace. It must preserve the current `/api` paths, accept `HEAD /api/health` with a 200 response, and use the existing application authentication and authorization checks. The API service must receive its Azure service credentials through workload identity or its own secrets; the Static Web App must not receive server credentials.
5. Render the ingress from this repository with `./scripts/render-portal-public-ingress.ps1 -Stack test` (or `prod`). Use `-ApiNamespace` and `-ApiServiceName` if the backend uses different names. Apply the rendered manifest after the API service and TLS secret exist; reapplying its controller is safe. Check that an HTTPS request to `/api/health` with the origin hostname succeeds.
6. Build the UI as static files and deploy them to the Static Web App. The current `probonolaw-ui` build is a standalone Next.js server with 38 server API routes, so its existing build artifact cannot be uploaded as static content. Move the routes and any server rendering or actions before switching users. The UI's browser API requests can keep their relative `/api/...` URLs through Front Door.
7. Verify the Front Door hostname serves UI paths and sends `/api/*` to the API origin. Test's `test.probono-law.com` custom domain is managed by Pulumi and attached to both Front Door routes. Its GoDaddy CNAME points to Front Door. Production's `probono-law.com` and `www.probono-law.com` custom domains attach to both routes. Add the `portalProductionWwwDomainValidationToken` output as GoDaddy TXT `_dnsauth.www` and wait for its managed certificate before relying on `www`. The apex validation TXT is `_dnsauth`. Require both domains to show validation `Approved`, certificate deployment `Succeeded`, and trusted HTTPS before removing the Production Web App.

## Production apex DNS staging and cutover

GoDaddy does not provide an apex CNAME for `probono-law.com`, and a Front Door IP is not stable. The Production Pulumi stack creates a public Azure DNS zone with the GoDaddy records represented: Azure supplies NS and SOA, Pulumi copies the application and mail records, and Pulumi adds the Front Door validation TXT records. Its apex A record initially stays at `203.0.113.153` through `productionLegacyApexIp`; `productionApexFrontDoor` is `false`. The `www` CNAME targets Production Front Door. The Azure zone has no effect while GoDaddy remains authoritative. The `portalProductionDnsNameServers` output lists its nameservers.

Before moving the registrar nameservers, compare every record and TTL between both authoritative zones, including `test`, the API origin records, wildcard, `www`, Microsoft 365 MX/TXT/CNAME/SRV records, and Front Door validation TXT records. Check that the registrar has no DNSSEC DS record tied to the old provider. Allow the previous NS TTL to expire after delegation and verify public resolution and mail. This delegation keeps the apex at the legacy portal.

Only after the Production Static Web App, AKS API, Front Door routes, both hostname certificates, sign-in redirect, and end-to-end tests are ready, change `probonolaw-infrastructure:productionApexFrontDoor` to `true` and apply the Production stack. Pulumi then updates the Azure DNS apex A record to an alias targeting the Production Front Door endpoint. Test `https://probono-law.com/`, `/api/health`, and sign-in. Setting the flag back to `false` and applying the stack restores the legacy A record if rollback is needed. Wait for the previous 600-second apex TTL before assuming all recursive resolvers have switched.

## Retire the legacy portal sites

`keepLegacyPortalWebApp` is `false` in Test and `true` in Production during staging. Setting it to `false` removes the Web App, App Service plan, site private endpoint and its DNS zone group, and the site's Blob and Table role assignments. Shared portal storage, its private endpoints, Application Insights, and Log Analytics remain. The Production program refuses to remove the site while `productionApexFrontDoor` is `false`.

Before setting the Production flag to `false`, verify the public apex and `www` both serve the static UI with trusted TLS, `/api/health` succeeds through Front Door, and browser sign-in works. The wildcard `*` CNAME points to Front Door in GoDaddy and the staged Azure DNS zone, but no wildcard custom domain or certificate is configured. Confirm that no required hostname depends on that wildcard, then remove it from GoDaddy. Pulumi removes the matching Azure DNS wildcard when the Web App is retired. Apply the Production stack only after those checks; the Production infrastructure workflow is manual.

Front Door Standard requires a public origin. Before production cutover, restrict direct access to the API origin to Azure Front Door backend traffic and validate the profile's `X-Azure-FDID` value against `portalFrontDoorGuid`. Keep health probes accessible. This ingress is separate from the private AIMIE routes. Review large document uploads against Front Door request-size limits during application testing.

Front Door's profile-level origin response timeout is set to its maximum of 240 seconds in both stacks. The ingress template allows 300 seconds between upstream reads and writes so it does not time out first. A synchronous API operation that sends no response for five minutes cannot reliably pass through Front Door Standard. Move such operations to an asynchronous API that returns a job ID promptly and exposes status/results through shorter `/api` requests. Review application and browser client timeouts separately.
